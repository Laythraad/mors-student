# قاعدة البيانات والترحيل (Database Migration)

## القاعدة الحالية

- **المحرّك الافتراضي:** SQLite — `DATABASE_URL=sqlite:///<جذر المشروع>/mors.db`.
- **طبقة الوصول:** SQLAlchemy 2.x مع نماذج ORM في `backend/app/db/`.
- لا يوجد Alembic عمداً: قاعدة SQLite الملفية لا تحتاج خدمة ترحيل، والمشروع
  يطبّق ترحيل **آنياً عند الإقلاع** (أدناه). التبديل إلى PostgreSQL ممكن عبر
  `DATABASE_URL` بعد مراجعة الأعمدة الخاصة بـ SQLite في `db/__init__.py`.

## كيف تُنشأ/schema عند الإقلاع

`lifespan` في `app/main.py` يستدعي `init_db()` (= `db/__init__.py`):

1. **`Base.metadata.create_all(engine)`** — ينشئ الجداول الناقصة فقط
   (لا يغيّر الجداول الموجودة).
2. **`_migrate_existing_tables()`** — يرفع القواعد القديمة إلى المخطط الحالي:
   - يقرأ `PRAGMA table_info` لكل جدول وينفّذ `ALTER TABLE ... ADD COLUMN`
     لكل عمود ناقص (مع DEFAULT/NOT NULL شرعية لـ SQLite).
   - يعالج الخاصيات التي لا تقبلها SQLite في مكانها (مثال: تحويل
     `questions.quiz_id` إلى nullable لبنك الأسئلة عبر إعادة بناء الجدول
     `questions_rebuild` ثم استبداله مع إعادة إنشاء الفهارس).
   - يعمل بـ `PRAGMA foreign_keys=OFF` داخل معاملة ثم يعيدها `ON`.

النتيجة: **تشغيل نسخة أقدم من الكود على قاعدة أحدث/أقدم يُصحَّح تلقائياً عند
الإقلاع** — لا خطوة يدوية.

## إضافة تغيير schema جديد (منهج العمل)

1. عدّل/أضف النموذج في `backend/app/db/models_*.py` (لا تنسَ التسجيل في
   `db/__init__.py` إن أضافة ملفاً جديداً).
2. إن كان التغيير «عمود جديد» — لا تكتب شيئاً: `_migrate_existing_tables`
   يضيفه تلقائياً عند أول إقلاع.
3. إن كان التغيير معقّداً (تغيير قيد، دمج جداول، تحويل نوع) — أضف خطوة
   صريحة داخل `_migrate_existing_tables()` بنفس نمط إعادة بناء `questions`.
4. شغّل الاختبارات: `python -m pytest -q` ثم `python -X utf8 tools/smoke_api.py`
   (تخلق قاعدة جديدة في `%TEMP%` فتختبر المسار من الصفر) **وزرّع قاعدة قديمة
   لتجربة الترحيل**.

## النسخ الاحتياطي والاستعادة

```powershell
# نسخة (SQLite ملف واحد + قد يكون -wal/-shm أثناء التشغيل)
Copy-Item mors.db backup\mors-$(Get-Date -Format yyyyMMdd).db

# الاستعادة: أوقف الخادم، انسخ الملف عائداً، شغّل
```

مع تشغيل مستمر يفضّل نسخاً ذرياً عبر `sqlite3 mors.db ".backup out.db"`
أو إيقاف الخادم أولاً حتى تُدمج ملفات WAL.

## ربط قاعدة مختلفة

- تطوير: عدّل `DATABASE_URL` في `.env` (جذر المشروع — مكانه ثابت في `app/config.py`).
- اختبار: يضبطه السكربت نفسه (مثال `tools/smoke_api.py` يحذف
  `%TEMP%\mors_api_smoke.db` ويحدّد `DATABASE_URL` إليه) — لا تعدّل يدوياً.
- إنتاج: مسار مطلق على قرص دائم مع صلاحيات كتابة لمستخدم الخدمة فقط.

## الزرع (seed) وعلاقته بالترحيل

- `seed_if_empty()` ينفَّذ عند الإقلاع **و`DEMO_DATA=true` فقط**:
  جداول فارغة ← منهج كامل + حسابات تجريبية؛ قاعدة فيها مستخدمون ← يُتخطّى
  إلا ما يكمله (مثل إضافة مرحلة الرابع المهني إن غابت، وصفحات الكتب الناقصة).
- الزرع لا يمسّ بيانات المستخدمين أبداً وهو آمن للتشغيل المتكرر.
- حسابا `demo@mors.ai` و`admin@mors.ai` مختومان (`SEALED_EMAILS`) لا يُحذفان
  عبر ميزة حذف الحساب §128.
